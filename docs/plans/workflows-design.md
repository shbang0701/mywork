# 업무 탭 설계 — 스크립트를 폼으로 실행하는 틀

업무 탭에 기능이 계속 늘어도, 기능 하나를 넣고 고치고 빼는 일이 **파일 하나**로 끝나게 하는 설계입니다.
업무 기능은 앱 안이 아니라 `scripts/`의 스크립트 하나로 만들고, 업무 탭은 그 스크립트를 폼으로 실행하고 기록하는 일만 맡습니다.

- 상태: 업무 탭 1단계를 만들었습니다(`apps/WorkTool/wpf/addons/workflows/`). 사용법은 [WPF README 「업무」](../../apps/WorkTool/wpf/README.md#업무), 화면은 [디자인 README](../../apps/WorkTool/design/README.md#업무-실제-화면)에 있습니다.
- 화면 배치(왼쪽 목록 · 가운데 입력 폼 · 오른쪽 설명)는 [업무 탭 사용법과 결과 미리보기](workflows-preview.md)의 목업을 따릅니다. 다만 1단계는 **스크립트 하나를 값과 함께 실행**하는 모델입니다. 목업의 단계 잇기 · 공통 기능 등록은 2단계 이후입니다(「단계」).
- 함께 볼 것: 스크립트 규칙은 [AGENTS.md](../../AGENTS.md) 「코드 규칙」, 앱의 탭을 폴더로 더하고 빼는 방법은 [WPF README](../../apps/WorkTool/wpf/README.md#탭애드온-더하기--빼기).

## 용어

| 말 | 뜻 |
|---|---|
| 업무 탭 | WorkTool WPF의 탭 하나(`apps/WorkTool/wpf/addons/workflows/`). 스크립트를 고르고 값을 넣어 실행합니다 |
| 업무 기능 | 업무 탭에서 실행하는 스크립트 하나(`scripts/<분류>/동사-명사.ps1`) |
| 업무 | 자주 쓰는 실행을 저장한 것: 스크립트 하나 + 칸 값 + 실행 방식. 업무 PC의 앱에서 만듭니다 |
| 코어 | 모든 탭이 같이 쓰는 앱 코드(`apps/WorkTool/wpf/core/`) |
| 묶음 파일 | 앱 전체를 파일 하나로 묶은 `apps/WorkTool/dist/WorkTool-WPF.ps1`. 업무 PC는 이 파일을 복사해 씁니다 |
| 데이터 폴더 | 앱이 저장하는 곳. 기본은 `문서\WorkTool`이고 저장소에 올라가지 않습니다 |

## 왜 스크립트인가

기능을 앱 안에 계속 넣으면 묶음 파일이 계속 커집니다. 그러면 하나만 고쳐도 업무 PC에 그 큰 파일을 통째로 다시 옮겨야 합니다.

| 업무 기능을 스크립트로 두면 | 이유 |
|---|---|
| 새 기능은 스크립트 파일 하나 | 업무 PC에는 그 파일만 옮깁니다. 업무 탭이 자리 잡으면 앱은 거의 바뀌지 않습니다 |
| LLM 없이 늘릴 수 있음 | `scripts/_template.ps1`대로 쓰고 콘솔에서 먼저 돌려 본 뒤 스크립트 폴더에 넣으면 업무 탭에 바로 보입니다 |
| 위험한 작업은 두 단계로 | 공유 폴더 삭제 · 권한 변경 같은 스크립트는 `-WhatIf`로 할 일만 보는 [미리보기] 뒤에 [실행]합니다 |
| 설명하기 쉬움 | 보안 쪽에 설명할 때 그 기능의 파일 하나만 보여 줍니다. 하나가 망가져도 다른 기능은 그대로입니다 |
| 회사 정보가 저장소에 안 올라감 | 실제 서버 · 공유 폴더 이름은 업무 PC에만 남습니다: 데이터 폴더(저장한 업무 · 실행 기록)와, 업무 PC에서 고친 스크립트 설정 블록 |

## 지키는 규칙

1. **업무 기능 하나, 탭 하나를 넣고 고치고 빼는 코드는 파일(폴더) 하나입니다.** 업무 기능은 스크립트 파일 하나, 앱의 탭은 `apps/WorkTool/wpf/addons/<이름>/` 폴더 하나입니다. 루트 `README.md`와 `scripts/README.md` 목록에 한 줄을 더하거나 지우는 문서 일은 따로 합니다.
2. **코어에는 탭 이름을 쓰지 않습니다.** 탭의 설명 · 검사 · 설정 기본값은 그 탭 폴더 안에 둡니다. 설정 값 자체는 데이터 폴더의 `settings.json`에 저장되지만, 기본값과 읽는 코드는 그 탭 파일에 있습니다. 코어 검사는 가짜 탭으로 합니다.
   - 예외: 색 · 글꼴 · 컨트롤 모양은 공통 UI 모듈(`core/Ui.psm1`)에만 둡니다(`AGENTS.md` 「앱(GUI) 원칙」). 탭에 새 모양이 필요하면 그곳에 쓰임새 이름으로 더합니다. 탭을 빼도 남은 모양은 다른 화면에 영향이 없어서 그대로 둬도 됩니다.
3. **업무 기능끼리, 탭끼리 서로 부르지 않습니다.** 그래야 하나를 빼도 다른 것이 깨지지 않습니다.
   - 스크립트는 다른 스크립트를 부르지 않습니다. 이어 쓸 때는 1단계에서는 사람이 앞 결과를 다음 칸에 넣고, 2단계부터는 업무 탭이 잇습니다.
   - 탭은 다른 탭을 부르지 않고, 홈 카드 · 도움말처럼 각 탭이 실행할 때 스스로 등록하는 목록(`Register-WtAddon`)을 거칩니다. 코어 파일을 고치는 목록이 아닙니다.
4. **약속은 작게 정하고, 늘릴 때는 선택 항목으로만 더합니다.** 그래야 예전 스크립트가 계속 돕니다.
5. **규칙 검사를 자동으로 돌립니다.**
   - 저장소: 업무 탭 폴더의 검사(`Test-Workflows.ps1`)가 `scripts/`의 모든 스크립트를 업무 탭과 같은 방법으로 읽습니다. 도움말 · param을 읽을 수 있는지, 금지 명령(`AGENTS.md` 「코드 규칙」 4번)이 없는지 봅니다. 전체 검사(`tests/Test-Core.ps1`)가 돌립니다.
   - 앱: 목록을 만들 때 읽지 못한 스크립트는 그 자리에 이유를 보이고 [실행]을 비활성으로 둡니다.

| 하는 일 | 고치는 코드 | 업무 PC로 옮길 것 |
|---|---|---|
| 업무 기능 추가 · 수정 | 스크립트 파일 하나 | 그 스크립트 하나 |
| 업무 기능 삭제 | 스크립트 파일 하나를 지움 | 업무 PC에서도 지움. 그 스크립트를 쓰던 업무에만 「스크립트 없음」이 뜹니다 |
| 업무 만들기 · 고치기 | 없음 | 없음. 업무 PC의 앱 화면에서 합니다 |
| 탭 추가 · 삭제 | 탭 폴더 하나. 전체 검사를 통과한 뒤 묶음 파일을 다시 만듭니다 | `WorkTool-WPF.ps1` |
| 업무 탭 자체를 고침 | 업무 탭 폴더. 전체 검사를 통과한 뒤 묶음 파일을 다시 만듭니다 | `WorkTool-WPF.ps1` |

## 스크립트 약속

`scripts/_template.ps1`로 만든 스크립트는 대부분 이미 이 약속을 지킵니다. 업무 탭은 스크립트를 **실행하지 않고 구문만 읽어서**(PowerShell 구문 분석기) 목록과 폼을 만듭니다.

**꼭 지킬 것**
- 맨 위 도움말: `.SYNOPSIS`는 목록에 보이는 한 줄입니다. `.DESCRIPTION` · `.EXAMPLE` · `.NOTES`는 설명 패널에 그대로 보입니다(`.NOTES`의 `WorkTool: 콘솔` 줄은 빼고).
- 실행할 때마다 바뀌는 값(대상 목록 파일, 서버 이름, 공유 폴더 이름 등)은 `param`으로 받습니다. 폼의 칸이 됩니다.
  - 칸 설명은 `.PARAMETER 이름`에 쓰거나, 없으면 param 줄 끝의 주석을 씁니다.
  - 경로 · 시트 이름 · 열 위치처럼 환경마다 한 번 정하는 값은 지금처럼 설정 블록에 둡니다. 이것은 파일을 고쳐서 바꾸는 값이고, param은 실행할 때 넣는 값입니다.
- **비우면 설정 블록 값을 쓰게 하려면** param에 기본값을 주지 않고, 설정 블록 아래 본문에서 들어온 값만 덮어씁니다. param 줄의 기본값(`= $Config.HostFile`)은 설정 블록보다 먼저 계산돼서 쓸 수 없습니다. [Watch-MultiPing.ps1](../../scripts/network/Watch-MultiPing.ps1)이 이렇게 씁니다.

  ```powershell
  param(
      [string]$HostFile   # 대상 목록 파일 (비우면 설정 블록의 HostFile)
  )
  $Config = @{ HostFile = Join-Path $PSScriptRoot 'ping-hosts.txt' }
  if ($PSBoundParameters.ContainsKey('HostFile')) { $Config.HostFile = $HostFile }
  ```
- 끝까지 해냈으면 종료 코드 0, 실패하면 오류로 끝냅니다. 템플릿의 `$ErrorActionPreference = 'Stop'`이면 그렇게 됩니다.
- 앱 안에서 실행할 스크립트는 `Read-Host`처럼 키 입력을 기다리지 않습니다. 업무 탭은 입력을 닫고 `-NonInteractive`로 실행해서, 입력을 기다리면 기다리지 않고 오류로 끝납니다. 입력이 필요하면 아래 「콘솔 창」 방식을 씁니다.

**param 종류에 따른 폼 칸**

| param | 폼 칸 |
|---|---|
| `[string]` | 입력칸 |
| `[string]` + `[ValidateSet(...)]` | 고르기 칸. 필수가 아니면 맨 위에 `(기본값)`이 있어서 넘기지 않을 수 있습니다 |
| `[int]` · `[double]` (+ `[ValidateRange(...)]`) | 숫자 칸. 숫자가 아니거나 범위를 벗어나면 칸 아래에 오류를 보이고 실행하지 않습니다 |
| `[switch]` | 체크 상자. 체크하면 `-이름`을 넘기고, 끄면 넘기지 않습니다. 기본값이 켜진(`= $true`) 스위치는 끌 때 `-이름:$false`를 넘깁니다 |
| 이름이 `File`로 끝나는 `[string]` | 입력칸 + [찾아보기] 버튼. 있는 파일을 고르는 창이 뜹니다 |
| 이름이 `Folder`로 끝나는 `[string]` | 입력칸 + [찾아보기] 버튼. 폴더를 고르는 창이 뜹니다 |
| `[Parameter(Mandatory)]` | 라벨 뒤에 `(필수)`. 비우면 실행하지 않습니다 |
| 그 밖의 종류(`[string[]]` · `[bool]` · `[datetime]` · `[hashtable]` 등) | 폼에 나오지 않고 스크립트 기본값을 씁니다. 칸 목록 아래에 「폼에서 넣을 수 없는 값 n개」로 알립니다. 이런 param이 필수이면 그 스크립트는 콘솔 창에서만 실행하고, 그 이유를 칸 목록 위에 알립니다. 창에서 PowerShell이 그 값을 직접 묻습니다 |
| 비밀 값: 이름에 `Password` · `Pwd` · `Secret` · `Token` · `ApiKey` · `Credential`이 들어가거나 `[securestring]` · `[pscredential]` | 폼에 나오지 않습니다. 저장한 업무 · 실행 기록 · 명령줄에 남지 않게 하려는 것입니다. 필수이면 콘솔 창에서 실행해 스크립트나 PowerShell이 직접 묻게 합니다 |

- 이름이 `Path`로 끝나는 칸은 파일인지 폴더인지, 있는 것인지 새로 만들 것인지 알 수 없어서 [찾아보기] 없이 입력칸만 둡니다. [찾아보기]가 필요하면 이름을 `...File` · `...Folder`로 짓습니다.

- 여러 값이 필요하면 `[string[]]` 대신 목록 파일 경로를 받거나(`-HostFile`처럼), `[string]` 하나로 받아 스크립트 안에서 쉼표로 나눕니다.
- 기본값이 글자 · 숫자 그대로이면 칸에 채워 둡니다. 식으로 된 기본값은 칸을 비워 둡니다.
- 비운 칸은 넘기지 않습니다. 스크립트는 자기 기본값(보통 설정 블록 값)을 씁니다.

**선택 항목**
- `[CmdletBinding(SupportsShouldProcess)]`가 있으면 [미리보기] 버튼이 생깁니다. `-WhatIf`를 붙여 실행해서 할 일만 보여 줍니다.
- 도움말 `.NOTES`에 `WorkTool: 콘솔` 줄이 있으면 실행 방식의 기본값이 「콘솔 창」이 됩니다. 자기 화면이 있거나 키 입력을 받는 스크립트에 씁니다. 업무마다 실행 방식을 바꿀 수 있습니다.
  - `Watch-MultiPing.ps1`에 이 줄이 있습니다. 콘솔 창에서 Q로 끝내야 요약 CSV가 남고, 창을 X로 닫으면 남지 않을 수 있습니다. 앱 안으로 바꾸면 Q를 받을 수 없으므로 `Rounds` 칸에 횟수를 넣어 실행합니다.

## 화면과 동작 (업무 탭 1단계)

색 · 크기는 `apps/WorkTool/design/README.md` 값만 씁니다.

- **왼쪽 목록**: 저장한 업무, 그리고 스크립트 폴더의 스크립트를 폴더별로 보여 줍니다. 스크립트 폴더는 [폴더 추가]로 고르고(앱의 문서 탭에서 볼 폴더를 고르는 것과 같은 방식), 그 아래 하위 폴더 3단계까지 `.ps1`을 찾습니다. 이름이 `_`로 시작하는 파일(`_template.ps1`)은 빼고, 없어진 폴더는 「폴더 없음」으로 보입니다.
- **기본 스크립트 폴더**: 아래 두 곳은 [폴더 추가] 없이 처음부터 목록에 있습니다. [목록에서 빼기]로 빼면 그것을 기억해서 다시 생기지 않고, 같은 폴더를 [폴더 추가]하면 다시 보입니다.

  | 목록 이름 | 폴더 |
  |---|---|
  | 내 스크립트 | 데이터 폴더의 `scripts`(기본 `문서\WorkTool\scripts`). 없으면 앱이 만듭니다 |
  | 예제 스크립트 | 앱 파일 옆 `scripts`(개인 PC zip을 푼 곳). 저장소 원본으로 띄우면(`start-dev.cmd`) 저장소 맨 위 `scripts/`. 앱 폴더 위로 3단계 안에서 `_template.ps1`이 있는 `scripts`만 잡습니다 |
- **가운데 폼**: 고른 스크립트의 param으로 만든 칸입니다. 명령은 [실행] 버튼(화면의 주 버튼) · [미리보기] · [취소], 실행 방식(앱 안 · 콘솔 창), [업무로 저장]입니다.
- **결과**: 앱 안 실행은 표준 출력과 오류 출력을 한 칸에 줄 단위로 바로 보여 주고, 끝나면 `성공` · `실패` · `취소`와 걸린 시간을 보입니다. 콘솔 창 실행은 창을 띄웠다는 것과, 앱이 켜져 있는 동안 창이 닫히면 닫힌 시각만 보입니다.
- **오른쪽 설명**: 스크립트 도움말과, 실행 기록 중 그 스크립트의 것을 최근 순으로 보여 줍니다. 접고 펼칠 수 있습니다. 창이 좁아 세 칸이 다 안 들어가면 접혀 있고, 펼치면 가운데 위에 겹쳐 뜹니다(Esc로 닫기).
- 앱 안 실행은 한 번에 하나입니다. 실행 중에는 [실행]을 비활성으로 두고 이유를 툴팁으로 보입니다. 콘솔 창은 따로 도는 창이라 여러 개를 띄울 수 있습니다.
- 저장한 업무의 스크립트가 바뀌어 없는 param의 값이 생기면 그 값은 넘기지 않고 칸 위에 알립니다. 새로 생긴 필수 칸은 채워야 실행합니다.

## 실행 방식

| 방식 | 하는 일 | 쓰는 곳 |
|---|---|---|
| 앱 안 (기본) | 창 없는 `pwsh -NoLogo -NoProfile -NonInteractive -File <스크립트> -이름:값 …`. 출력은 앱이 받아서 보여 줍니다 | 끝나면 결과를 내는 스크립트 |
| 콘솔 창 | 보이는 PowerShell 창에서 `pwsh -NoLogo -NoProfile -NoExit -File <스크립트> -이름:값 …`. 끝나도 창이 남아 출력을 읽을 수 있고, 사용자가 창을 닫습니다 | 자기 화면 · 키 입력이 있는 스크립트, 끝낼 때 정리가 꼭 필요한 스크립트 |

- 두 방식 모두 작업 폴더는 그 스크립트 파일이 있는 폴더입니다(등록한 스크립트 폴더가 아님).
- 콘솔 창은 스크립트가 끝나도 셸이 계속 돌기 때문에 앱이 스크립트의 결과와 종료 코드를 알 수 없습니다. 그래서 기록에는 결과 대신 `콘솔 창`이 남습니다.

- 값은 `-이름:값` 모양의 인수 하나로 넘깁니다. 띄어쓰기 · 따옴표 · `-`로 시작하는 값도 그대로 전달됩니다. 입력값으로 명령 문자열을 조립하는 `-Command`는 쓰지 않습니다.
- [미리보기]도 [실행]과 같은 실행 방식으로 돌립니다.
- [취소]는 앱 안 실행의 프로세스를 자식 프로세스까지 끝냅니다. 이때 스크립트의 `finally`는 돌지 않을 수 있습니다(`Watch-MultiPing.ps1`의 요약 파일 등). 그래서 그런 스크립트는 콘솔 창에서 실행하고 그 창에서 끝냅니다. 콘솔 창은 앱이 닫지 않습니다.
- 앱을 끄면 앱 안 실행도 멈춥니다. 창 없는 프로세스를 남기지 않기 위해서입니다. 콘솔 창은 그대로 둡니다.
- 출력은 시스템의 OEM 코드 페이지로 읽습니다(한국어 Windows는 949, 「UTF-8 사용」을 켜면 65001). 사용자 형식(문화권) 설정과는 상관없습니다. 오류 글자의 색 코드가 섞이지 않게 환경 변수 `NO_COLOR=1`을 줘서 실행합니다.
- 출력은 화면과 따로 도는 실행 공간이 쉬지 않고 읽어 둡니다. 출력이 많아도 스크립트가 화면을 기다리느라 느려지지 않습니다. 화면에는 최근 2,000줄 정도만 둡니다.
- 스크립트가 끝난 뒤에도 그 스크립트가 띄운 프로그램(`Start-Process -NoNewWindow` 등)이 출력 통로를 붙잡고 있으면, 2초 기다린 뒤 끝으로 봅니다. 그 프로그램은 끄지 않고, 그 뒤 출력은 받지 않습니다.
- 실행 정책은 바꾸지 않습니다. `-ExecutionPolicy` · `-EncodedCommand`를 쓰지 않습니다. 실행 정책에 막히면 그 오류가 출력에 보이고 결과는 `실패`입니다.
- 스크립트 파일을 새로 쓰거나 내려받지 않습니다. 사용자가 폴더에 넣은 파일을 그대로 실행합니다.

## 저장하는 것

모두 데이터 폴더에 있고 저장소에는 올라가지 않습니다. 저장은 코어의 저장 함수만 거칩니다.

| 이름 | 내용 | 크기 |
|---|---|---|
| `settings.json`의 `workflows.roots` | [폴더 추가]한 스크립트 폴더 목록 | |
| `settings.json`의 `workflows.hiddenRoots` | 목록에서 뺀 기본 스크립트 폴더 | |
| `workflows.json` | 저장한 업무: 이름 · 스크립트 전체 경로 · 칸 값 · 실행 방식 | |
| `workflow-runs.json` | 실행 기록: 시작 시각, 스크립트, 넘긴 값, 실행 방식. 앱 안 실행은 끝 시각 · 결과 · 종료 코드 · 출력 마지막 40줄도 남깁니다. 콘솔 창은 앱이 켜져 있는 동안 창이 닫히면 닫힌 시각만 더합니다 | 모든 스크립트를 합쳐 최근 100건 |

- 스크립트가 만드는 결과 파일(CSV · Excel)은 스크립트가 직접 저장합니다. 업무 탭은 사용자 결과 파일을 만들지 않습니다.
- 스크립트 파일이 옮겨지면 그 업무에 「스크립트 없음」을 보이고, [스크립트 다시 고르기]로 고칩니다.

## 업무 PC로 가져가기

- 스크립트: GitHub에서 필요한 스크립트만 복사해 `문서\WorkTool\scripts`(업무 탭의 「내 스크립트」)에 같은 이름으로 저장합니다. 분류 폴더(`files\` 등)를 만들어 넣어도 됩니다. [폴더 추가]는 필요 없고, 업무 탭에 다시 들어오거나 F5를 누르면 보입니다.
- 예제: 저장소 `scripts/`의 스크립트는 그대로 쓸 수 있는 예제입니다(사무 · IT 운영 · IT 개발, 목록은 [scripts/README.md](../../scripts/README.md)). 개인 PC zip에는 `scripts\`로 같이 들어 있어서, 풀고 켜면 「예제 스크립트」에 바로 보입니다. 업무 PC에서 처음 써 볼 때는 읽기만 하는 확인용 스크립트(`Get-DiskSpace.ps1` 등)부터 돌려 봅니다.
- 앱: 업무 탭 자체가 바뀔 때만 `apps/WorkTool/dist/WorkTool-WPF.ps1`을 다시 복사합니다.

## 단계

| 단계 | 내용 |
|---|---|
| 업무 탭 1단계 | 스크립트 폴더 · 목록, param으로 만든 폼, 앱 안 · 콘솔 창 실행, 미리보기(`-WhatIf`), 취소, 업무로 저장, 실행 기록, 스크립트 약속 검사 |
| 업무 탭 2단계 | 여러 스크립트 잇기(앞 단계 결과를 다음 단계 값으로), 결과를 표로 보기, 결과에 따라 WorkTool 알람 예약. 스크립트가 혼자 할 수 없고 앱만 할 수 있는 일입니다 |

- 1단계에서 이어서 하려면, 앞 스크립트가 출력에 보여 준 결과 파일 경로를 복사해 다음 스크립트 칸에 넣습니다.
- 2단계의 알람은 WorkTool이 켜져 있는 동안 앱 안에서 울리는 알림입니다(일정 탭의 알람과 같음). Windows 작업 스케줄러 같은 자동 실행 등록은 쓰지 않습니다(`AGENTS.md` 「코드 규칙」 4번).
- Office 양식 채우기처럼 무거운 일도 업무 기능이라 스크립트(`scripts/office/`)로 만듭니다. 앱은 그 스크립트를 실행만 합니다. DRM 문서 내용을 평문으로 빼내는 스크립트는 만들기 전에 먼저 확인합니다(`AGENTS.md` 「코드 규칙」 6번).
- 이 설계는 [미리보기 목업](workflows-preview.md)이 후속으로 미뤄 둔 「사용자 스크립트 실행」을 1단계로 당긴 것입니다. 목업의 「공통 기능 등록」(앱 기능마다 이름 · 입력 · 결과 형식을 정해 두고 단계에서 고르게 하는 방식)은 2단계의 잇기 · 알람에 씁니다.
- 나중에 앱이 직접 사용자 결과 파일을 만들게 되면 출력 개수 · 용량 한도를 함께 붙입니다. 그때 Codex가 만들어 둔 출력 한도 모듈을 고쳐 씁니다.
